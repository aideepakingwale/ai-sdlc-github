# DevMind — Agile delivery & the `.devmind/` index

Status: **design, for review** · Branch: `feature/devmind-agile-index`

## 1. Decisions already made

| # | Question | Decision |
|---|---|---|
| 1 | Where do index files live? | **In the customer's repository only**, in a dot-folder (`.devmind/`), committed like `.claude/` or `.kiro/`. The repo is the system of record. |
| 2 | Do humans edit them? | **No. Read-only, machine-generated.** Their structure belongs to DevMind. Humans change *inputs* (backlog, approvals), never the index. |
| 3 | Typical project length | Unknown; designed for **1–100+ sprints** (see §7) with a constant-size context at any length. |

## 2. Goals and non-goals

Goals: support incremental (Scrum/Kanban) delivery on top of the existing stage DAG; keep every agent prompt
bounded regardless of project age; make history auditable, diffable and portable with the code.

Non-goals: a Jira replacement (the backlog may sync from Jira); human-editable indexes; a vector database inside
the repo.

## 3. Principles

1. **Never feed history, feed a packet.** Agents get a budgeted context assembled for the task, not "all upstream".
2. **Structured facts, short prose.** Facts are fields and IDs (survive summarising); prose is a few lines, always
   with a pointer back to source.
3. **Append-only, one file per event.** A sprint writes its own files; nothing shared is rewritten. This makes
   concurrent branches and parallel sprints merge without conflicts.
4. **LLM decides, code enforces.** The LLM writes summaries and relevance judgements; deterministic code owns
   the schema, hashes, IDs, budgets and what is loaded.
5. **Governance preserved.** Index commits are *queued* during generation and committed only after the gate is
   approved, through the existing deferred-publish path, attributed to the approver.

## 4. Repository layout

```
.devmind/
  README.md                      # "Generated by DevMind — do not edit" + schema version
  manifest.json                  # tiny: schemaVersion, project id, current release/sprint, file hashes
  charter.md                     # L0: vision, constraints, stack, Definition of Done, key decisions
  releases/
    R-2026-03/index.md           # L1: one per release (summary, scope, decisions, pointers)
    R-2026-03/index.json         # machine twin (authoritative for tools; md is a rendering)
  sprints/
    S-014/digest.md              # L2: goal, stories done, deltas, open issues, decisions
    S-014/digest.json
    S-014/delta-hld.md           # design delta (what changed and why)
  specs/                         # living specs, one current version per component
    api.md  data-model.md  architecture.md
  decisions/ADR-0007.md          # one file per decision (append-only)
  trace/S-014.json               # story → artifact → test links (IDs only)
  archive/                       # sprint digests rolled into a closed release
```

Every file starts with a header (`generatedBy`, `schema`, `sourceCommit`, `contentHash`). The manifest stores each
file's hash, so a human edit is **detected** (hash mismatch) and reported, never silently trusted.

## 5. The tiers and the budgeted context packet

| Tier | Content | Size target | Loaded |
|---|---|---|---|
| L0 | `charter.md` | ≤ 2k tokens | always |
| L1 | latest release index; older ones as one line each | ≤ 2k + 50 each | always |
| L2 | previous sprint digest + any the task references | ≤ 800 each | by relevance |
| L3 | full artifacts / living-spec sections | unbounded | only retrieved sections |

Assembly is code: fixed budget per tier, deterministic priority, lowest tier trimmed first, and the plan card
shows exactly what was included. The LLM may *propose* which L2/L3 items look relevant (by story/component IDs);
code verifies they exist and fit the budget.

Retrieval is **file-based**: the JSON twins carry IDs, component names and keywords. Embeddings are never
committed; the existing RAG index is rebuilt from the index files on demand, so the repo stays small and
deterministic.

## 6. How it fits the existing engine

* **Iteration dimension.** Stage state moves from `(project, stage)` to `(project, iteration, stage)`. Stages get
  `scope: project | iteration`. The graph stays acyclic; a sprint instantiates the iteration stages again.
* **Backlog.** Stories with acceptance criteria, derived from the PRD by a Refine agent; a Plan agent selects a
  sprint slice. The sprint slice reuses the existing *confirmed scope* mechanism (generate only these items).
* **Gates.** Mode per stage: `full` (review matrix), `lightweight` (one PO sign-off), `auto` (validator score ≥
  Definition of Done). Full gates at the architecture runway and release; light/auto per sprint.
* **Write path.** Sprint/release close → the index writer renders files → queued as `github_commit_*` actions →
  committed by `PublishService` on approval. Reuses `github.commitFiles`.
* **Read path.** **New dependency:** the connector has no tool to read files/trees from the repo. Add
  `github_read_files` and `github_list_tree` (read-only, size-capped, ref-pinned) so the orchestrator can load
  `.devmind/` at a specific commit. A short-lived cache keyed by commit SHA avoids repeated API calls.
* **Staleness.** An amended approved artifact marks the digests/index entries that reference it as stale, as plan
  staleness works today.

## 7. Project length: industry norms, sizing and limits

*Industry norms (general knowledge, not measured on your data):* most Scrum teams run **2-week sprints** (range
1–4 weeks), release every **2–6 sprints**, and products live **6–24+ months** — about **26 sprints a year**, so
**13–52 sprints** for a typical project and **100+** for a long-lived product. Kanban has no sprints but the same
calendar length.

*Sizing at 26 sprints/year (approx.):*

| Item | Per unit | After 1 year | Loaded per task |
|---|---|---|---|
| Sprint digest | ~700 tokens | ~18k tokens total | 1–3 digests |
| Release index | ~1.5k tokens | 4–6 releases ≈ 8k | latest + one-liners |
| Charter | ~1.5k tokens | constant | always |

Reading everything would be ~28k tokens a year and growing; the packet stays **~5–8k tokens forever**.

*Risks and limitations of long projects — and mitigations:*

| Risk | Mitigation |
|---|---|
| Repo noise and history growth | One commit per sprint/release close; small text files; archive and roll up at release close |
| Merge conflicts across branches | Append-only per-sprint files; only `manifest.json` is shared and it is regenerated, never hand-merged |
| Index drift from the code | Hash and `sourceCommit` per file; drift report; regenerate from sources, never patch |
| Summary-of-summary decay | Facts as structured fields/IDs; prose short; links to source; digests roll up from structured data, not from other prose |
| Hallucination when retrieval misses | Reference check: statements about unknown components or stories are flagged |
| Secrets/PII reaching the repo | Existing output guardrail masks content before it is rendered; index files are scanned |
| Branch protection / required PRs | Configurable: direct commit to a bot branch, or open a PR; approval still gates it |
| GitHub API limits and file-size caps | Batch commits, size-capped reads, SHA-keyed cache; split any file that nears the cap |
| Schema evolution over years | `schemaVersion` in the manifest and a forward-only migrator; old files stay readable |
| Monorepos and many projects | `.devmind/` per project path with the project id in the manifest |
| Repo access revoked or rate-limited | Generation continues from the last cached commit; publish retries, per the existing queue semantics |
| Long-lived parallel releases (hotfix on an old release) | Releases are independent folders; hotfix digests attach to the release they patch |

## 8. Open items for the next review

1. Commit strategy: direct to the default branch, a dedicated `devmind/index` branch, or a PR per close?
2. GitHub App permissions: contents read **and** write on the target repo.
3. Is Jira the backlog of record (reference it) or is the backlog stored only in `.devmind/`?
4. Retention: how long are archived digests kept in the repo before they are dropped from the tree (history keeps them)?

## 9. Delivery plan

1. **Spike (this branch):** index schema + renderer (pure functions, unit-tested), manifest and hashing, and the
   budgeted packet assembler with a synthetic 60-sprint fixture proving the packet stays flat.
2. **Connector:** `github_read_files` / `github_list_tree`; write path through the publish queue.
3. **Engine:** iteration dimension and `scope` on stages; sprint instantiation.
4. **Backlog and agents:** Refine and Plan agents, sprint slicing on the confirmed-scope mechanism.
5. **Gates and increments:** gate modes, Definition of Done, delta artifacts and living-spec merge.
6. **UI:** sprint selector, board, burndown/velocity; drift and staleness indicators.

Acceptance for step 1: given a 60-sprint synthetic project the assembled packet is within budget, deterministic,
identical on re-run, and every pointer resolves.
