STAGE QUALITY BAR — Product definition (industry-standard Agile):
- Produce a real backlog HIERARCHY: Epic -> Feature -> User Story -> Sub-Task. Each epic carries a business case, a measurable success metric (metric, baseline, target) and a target quarter; each feature is a shippable capability with its own acceptance criteria; no epic has only one feature and no feature has only one story unless the scope is genuinely that small.
- Every story uses the structured form (as a / I want / so that), is INVEST-compliant and vertically sliced, is Fibonacci-estimated (1,2,3,5,8,13) with a one-line estimation rationale, and is split so none exceeds 8 points.
- Every story decomposes into technical SUB-TASKS estimated in hours (design, build, test, docs as appropriate) — enough that a team could start sprinting.
- Acceptance criteria are executable Gherkin (Given/When/Then) with concrete data, one behaviour per scenario, and at least one negative/edge scenario per story (validation failure, permission denied, idempotent replay, empty state).
- SHIFT-LEFT — each feature carries a "Technical feasibility & constraints" note (an architect's view: feasibility on the target stack, likely architectural/integration risks, anything hard/slow/costly) and each story carries a "Testability" note (a QA view: how it will be verified — test types, required test data, key negative/edge and non-functional checks). Any story whose acceptance criteria are not objectively testable must be refined or raised as an open question, not left as-is.
- The PRD includes: problem statement with evidence; objectives and success metrics as a table (metric, baseline, target, measured-by); in-scope and EXPLICIT out-of-scope; personas; primary user journeys; functional requirements; non-functional targets with numbers (availability SLO, p95/p99 latency, throughput, security, accessibility); data model with PII/sensitivity classification, retention and residency; dependencies and assumptions; risks with mitigations and owners; a release/rollout and measurement plan; and open questions with named owners.
- Include a first-class COMPLIANCE, LEGAL & REGULATORY section: infer the obligations the domain triggers (e.g. GDPR/UK-GDPR for personal data, PCI-DSS for card payments, HIPAA for health data, SOX for financial reporting, WCAG for accessibility, data-residency rules) and list each as a concrete, testable requirement with its trigger and owner. If an obligation plausibly applies but cannot be confirmed from the input, record it as a high-priority open question rather than silently deciding it does or does not apply. If none apply, state that explicitly with a one-line justification.
- Include a SHIFT-LEFT REVIEW section that consolidates the cross-functional view: technical-feasibility risks an architect would flag (with severity), testability gaps a QA lead would flag, and Engineering + QA listed among the stakeholders — so design and test concerns are surfaced now, not discovered downstream.
- End with a REQUIREMENTS CONFIDENCE & OPEN ITEMS section: an overall confidence level (High/Medium/Low) with justification; every assumption made to proceed; and every unresolved question (compliance/legal flagged as high priority) with a named owner. Confidence is High only when there are no unresolved compliance/legal gaps, no unresolved feasibility risk, and no assumption that would materially change scope, cost, architecture or security.
- Provide a Definition of Ready and a Definition of Done for the backlog.
- Set `jiraProjectKey` to a 2-6 uppercase-letter identifier derived from the product name (e.g. 'Agile Quality Demo Platform' -> AQDP); the epics/stories are keyed by it. If the reviewer's feedback asks to change the identifier, use exactly the key they specify.
